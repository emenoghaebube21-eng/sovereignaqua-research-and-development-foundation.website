ADMINISTRATION & DEVELOPMENT

Administrator & Developer Guide

Operational guidance for authorized administrators, developers, maintainers, and technical contributors of the SovereignAqua Research & Development Foundation website.

01 • PURPOSE

About This Guide

This guide establishes the technical and administrative standards for maintaining the SovereignAqua Research & Development Foundation website. It is intended to support continuity, responsible administration, secure development, and consistent publication of Foundation information.

Authorized Access Only

Administrative functions, source-code repositories, deployment services, domain settings, credentials, databases, payment systems, and other infrastructure must only be accessed by individuals expressly authorized by the Foundation.

02 • ADMINISTRATION

Administrative Responsibilities

Website Administrator

Maintains published content, navigation, announcements, forms, media, and general website configuration.

Technical Administrator

Oversees hosting, deployment, domains, integrations, backups, technical configuration, and system availability.

Content Administrator

Reviews and publishes Foundation news, research, programmes, publications, events, and announcements.

Developer

Maintains source code, resolves defects, implements approved improvements, and follows the Foundation's development standards.

03 • DEVELOPMENT

Development Standards

  • Use semantic HTML5 wherever practical.
  • Maintain responsive layouts for desktop, tablet, and mobile.
  • Use accessible labels, headings, focus states, and keyboard navigation.
  • Keep JavaScript modules separated according to responsibility.
  • Avoid duplicate functions or competing initialization routines.
  • Use descriptive file, class, function, and variable names.
  • Do not place passwords, API keys, private tokens, or credentials in source code.
  • Optimize images and media before publication.
  • Test changes before publishing them to the production branch.
  • Preserve existing functionality unless a change has been intentionally approved.
04 • GITHUB WORKFLOW

Source-Control Procedure

  1. Create or use a dedicated development branch.
  2. Make one logical group of changes at a time.
  3. Review the complete file before committing.
  4. Use descriptive commit messages.
  5. Review all changed files before merging.
  6. Test the deployment preview where available.
  7. Resolve identified defects before approval.
  8. Merge approved changes into main.
  9. Verify the production deployment after merging.
Production Protection

The main branch should be treated as the production branch. History rewriting and force-push operations should be avoided except where a specific repository-maintenance procedure has been authorized and the existing history has been safely preserved.

05 • CONTENT MANAGEMENT

Publishing Foundation Information

Published information should be accurate, current, and capable of being supported by appropriate Foundation records.

Research

Verify research descriptions, authorship, publication information, dates, and supporting references.

Projects

Clearly distinguish active projects, completed projects, proposed initiatives, and future programmes.

Statistics

Maintain an internal source or record for published statistics, impact figures, partnerships, and milestones.

Partners

Do not publish an organization's name, logo, endorsement, or partnership claim without appropriate authorization.

06 • SECURITY

Security Requirements

  • Never publish passwords or private credentials.
  • Use strong authentication for administrative accounts.
  • Enable multi-factor authentication where supported.
  • Limit administrative access according to role.
  • Review third-party integrations periodically.
  • Remove access when an administrator or developer leaves the project.
  • Keep dependencies and external libraries reasonably current.
  • Do not expose private user information through public pages.
  • Never commit API keys, access tokens, passwords, private certificates, or other secrets to GitHub.
07 • DEPLOYMENT

Production Deployment Checklist

  1. Confirm the intended changes.
  2. Review modified files.
  3. Check internal links.
  4. Check image and video paths.
  5. Test navigation on desktop and mobile.
  6. Test forms and interactive components.
  7. Review browser console errors.
  8. Review accessibility and keyboard behavior.
  9. Verify the deployment preview.
  10. Merge the approved change.
  11. Verify the live website after deployment.
08 • MAINTENANCE

Routine Maintenance

Weekly

Review the homepage, navigation, forms, announcements, and critical links.

Monthly

Review content accuracy, dependencies, integrations, administrator access, and website performance.

Before Major Releases

Perform a complete functional, responsive, accessibility, security, and content review.

09 • INCIDENT RESPONSE

When Something Goes Wrong

  1. Identify the affected component.
  2. Determine whether the problem affects users, services, or data.
  3. Preserve relevant logs and error information.
  4. Avoid making multiple uncontrolled changes.
  5. Roll back the affected change when appropriate.
  6. Document the incident and corrective action.
  7. Verify the website after remediation.
10 • GOVERNANCE

Change Management

Significant changes to the website should be traceable to an approved requirement, issue, project task, or administrative decision. Changes should be documented through the Foundation's designated project and source-control systems.

Principle of Least Privilege

Administrative and technical permissions should be granted only to the extent necessary to perform an assigned responsibility.

11 • BACKUP & RECOVERY

Business Continuity

The Foundation should maintain recoverable copies of important website source code, configuration documentation, and other critical technical records.

  • Preserve important production commits and releases.
  • Keep critical configuration documentation separate from confidential credentials.
  • Never use the public repository as a storage location for passwords or private secrets.
  • Maintain an identified recovery procedure for significant website failures.
  • Periodically verify that important recovery resources remain accessible.
  • Document responsible personnel for restoration and technical recovery.
12 • ACCESS CONTROL

Administrative Access

Authorized Personnel

Administrative access should be limited to personnel who have a defined responsibility requiring that access.

Account Review

Access should be reviewed periodically and removed when it is no longer required.

Authentication

Strong authentication and multi-factor authentication should be used wherever the service supports them.

Sensitive Information

Credentials and confidential information should be transmitted only through approved secure channels.

13 • QUALITY ASSURANCE

Website QA Checklist

  • Page loads without fatal browser errors.
  • Navigation links resolve correctly.
  • Images and videos load from valid paths.
  • Responsive layouts work across supported screen sizes.
  • Interactive controls can be operated using a keyboard.
  • Forms provide appropriate labels and validation.
  • Important content has appropriate headings.
  • Published claims, dates, statistics, and partnership references have been reviewed.
  • No credentials or confidential information are exposed.
14 • CONTACT

Technical Support & Administration

Technical or administrative questions should be directed through the Foundation's authorized internal communication and support channels. Sensitive credentials or confidential information should never be submitted through a public website form.

Documentation Principle

Significant technical changes, incidents, configuration changes, and production releases should be documented so that authorized administrators and developers can understand what changed, why it changed, and how the system can be restored if necessary.
